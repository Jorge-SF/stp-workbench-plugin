# Known issues in the existing STP V2 tool

Findings about the current browser + Python flow that were found while porting it. They are recorded here and not fixed:
`reference/web/` is frozen, and the Python behaviour is unchanged.

## KI-1: sub-second bar times make the browser reject a package the bridge has already saved

**Short answer:** A real project with sub-second bar times does not fail to *apply*. It fails at *package preparation*
in the browser, with a misleading error. The bridge has already validated and saved the package and its ready receipt,
and script 3 would accept them. A user who believes the error will not run script 3.

### What normalizes

Python writes the same instant in three spellings:

| Where | Function | `06:30:00.25` is written as |
|---|---|---|
| Snapshot times (`start`, `finish`, `originalStart`, …) | `stp_v2_snapshot_contract._iso` | `2026-03-02T06:30:00.25` (trailing zeros removed) |
| Snapshot fragment ids | `stp_v2_core._fragment_id` (`datetime.isoformat()`) | `…:2026-03-02T06:30:00.250000:…` |
| The apply package the bridge stores and hashes | `stp_v2_apply_contract.load_apply_package` → `apply_package_to_json_value` (`isoformat()`) | `2026-03-02T06:30:00.250000` |

The browser planner writes times with `planner_logic.js` `addCivilDays` (line 49), which removes trailing zeros (`.25`),
like the snapshot. So for any package with a sub-second time, the bytes the browser hashes are not the bytes the bridge
stores. `POST /apply-package` (`stp_live_refresh_server_v2._save_apply_package`) re-serializes the parsed package and
returns the SHA-256 of **its** bytes as `package_sha256`.

Measured on the two golden packages with millisecond fractions (JS canonical bytes → Python-stored bytes):

| Golden package | JS SHA-256 | Python-stored SHA-256 |
|---|---|---|
| `engine_edges.fraction_tail_roundtrip` | `aa2e03bcbc4b…` | `fb680f8f9722…` |
| `engine_edges.fractional_cascade` | `92d963b79dc5…` | `88d83c62b939…` |

The full values are in `src/StpBridge.Tests/TestData/python_vectors.json` (`goldenNormalized`, generated by
`make_python_vectors.py` from the real contract code). `tools/golden/verify_canonical.py` does not see the difference,
because it re-dumps the parsed JSON without going through `load_apply_package`.

### What the existing flow does with it

1. **Bridge:** accepts the package (201). The datetimes compare equal after parsing, so validation and fragment-id matching
   pass. It writes `Respaldos_STPUG-VGS_v2/stp_apply_pending_v2.json` (normalized) and
   `stp_apply_pending_v2.ready.json` (hash of the normalized bytes).
2. **Browser** (`short_term_planner_template_v2.html`, `persistApplyPackageWhenLive`): it compares
   `receipt.package_sha256 !== digest`, where `digest` is the SHA-256 of its own canonical text. It throws
   *"El puente no confirmó el paquete exacto."*. That error has no HTTP status, so `prepareApplyPackage` shows the generic
   notice *"No se pudo validar y persistir el paquete en el puente local."* It does not download the package and does not
   mark it ready.
3. **Script 3** (`3. VGS_ApplySTPToVGS.py`, `find_latest_apply_package`): it checks only that the stored package matches
   the stored ready receipt. Both were written by the bridge, so they agree and the apply would go ahead.

The integration test `BridgeIntegrationTests.SubSecondTimesAreRenormalizedByTheServer` reproduces steps 1 and 3 against
the real bridge. It posts a package spelled the way `planner_logic.js` spells times, gets 201 with a receipt hash that
differs from the posted bytes' hash, and checks that the stored package and ready receipt agree.

### Who is affected

* Only projects whose VGS bars have times that are not whole seconds. `ticks_to_datetime` keeps microseconds
  (`ticks // 10`), so such times reach the snapshot whenever VGS stores them. **[UNVERIFIED]** how often VGS writes
  sub-second bar times in practice.
* The Workbench plugin is not affected. `StpBridgeClient.SubmitApplyPackageAsync` sends `ApplyPackage.ToCanonicalBytes()`,
  which already uses Python's `isoformat` spelling, so the receipt hash matches.

### Possible fixes (not done)

Have the bridge hash the received canonical bytes instead of the re-serialized ones, or have the browser compare its
receipt against Python's normalization. Either is a behaviour change to the existing tool and needs a decision first.

## KI-2 (fixed): the installed runtime folder was shared by every user of the PC

**Fixed 2026-11-19.** Script 2 now writes its runtime files to the per-user folder
`%LOCALAPPDATA%\Maptek\StpUGuntime` (override: `STP_RUNTIME_ROOT`), never beside itself. The rule lives in
`stp_core.runtime.default_runtime_root`, inline in script 2 (single-file bundles can't import it), and in C#
`PluginSession.DefaultRuntimeFolder`; tests on both sides check that they agree. The MSI no longer makes any folder
writable for Users.

What it was: script 2 wrote `<scripts>\.stp_ug_v2_runtime\` (the rendered HTML, the snapshot and, in plugin mode,
`plugin_session.json` with the bridge token). Under `C:\Program Files\Maptek\STP UG` normal users cannot write
there, so the first MSI (1.0.25) made that folder modifiable for the Users group, and every Windows user of the PC
could read the others' live bridge token.

Found with it and fixed in the same change: script 2 could not start from a checkout or an install at all.
`stp_core.runtime` looked for the bundle's file names (`stp_v2_planner_logic.js`, ...) while `reference/web` has
`planner_logic.js`, ..., required the Maptek logo that the public repository doesn't hold, and the MSI shipped no
web files. It now accepts both name styles, treats the logo as optional (blank footer image without it), and the MSI
ships `Client\Python\web\` (with the logo only when the builder has `installer\private\Maptek_highres.jpg`).
